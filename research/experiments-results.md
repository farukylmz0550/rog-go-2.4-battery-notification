# ROG Strix Go 2.4 - Experiment and Research Results

This document separates the experiments performed so far into two main categories: **confirmed findings / successful results** and **attempts that produced no results or remain unexplained**.

The goal is to clearly document which parts of the research have been established and which approaches should not be repeated without additional evidence.

---

## 1. Device Identity and Linux Connectivity

### ✅ Successful

The device was correctly identified under Linux.

- Product: `ASUS ROG STRIX Go 2.4`
- USB VID: `0x0B05`
- USB PID: `0x18D6`
- USB revision: `3765`
- USB speed: Full Speed
- HID interface: `1-1:1.3`
- HID driver: `usbhid`
- Device during testing: `/dev/hidraw5`

It was confirmed that the `hidraw` device number is not stable. Therefore, the application should not use a fixed path such as `/dev/hidraw5`; it should discover the device using VID/PID and device identification.

`udevadm info -q property -n /dev/hidraw5` successfully returned USB/HID properties for the ASUS device.

## 2. Linux Input Events

### ✅ Successful

The headset's Consumer Control interface provides standard media controls to Linux through `/dev/input/event18`.

Supported controls:

- `KEY_VOLUMEUP`
- `KEY_VOLUMEDOWN`
- `KEY_MUTE`
- `KEY_PLAYPAUSE`
- `KEY_NEXTSONG`
- `KEY_PREVIOUSSONG`

The multi-click behavior of the Play/Pause button was also verified:

- 1 click → Play/Pause
- 2 clicks → Next Track
- 3 clicks → Previous Track

These behaviors were observed through the Linux input layer.

### ⚠️ Partial Result / Unclear

`event19` and `event20` are also identified as `ASUS ROG STRIX Go 2.4`.

`event19`:

- `BTN_0`
- `ABS_MISC`, `0..13`

`event20`:

- `ABS_MISC`, `0..65535`

No meaningful changes were detected on these devices during normal button and control tests.

Their purpose is still unknown.

## 3. Physical Mute Button

### ✅ Successful, but expected behavior was not confirmed

The physical mute button is reported to Linux as `KEY_MUTE`.

However, during testing, pressing the button did not cause the PipeWire microphone source to enter the `MUTED` state. The `wpctl get-volume` output did not show a mute state, and the microphone continued capturing audio.

Result:

- The Linux input event generated by the button is known.
- Hardware-level microphone muting could not be demonstrated.
- Therefore, the `KEY_MUTE` event could potentially be connected to a PipeWire mute command in software later, but this should be treated as a separate feature.

## 4. PipeWire / ALSA Audio Devices

### ✅ Successful

The headset's actual audio devices are correctly recognized by PipeWire.

- Output: `ROG STRIX Go 2.4 Analog Stereo`
- Microphone: `ROG STRIX Go 2.4 Mono`

This confirms that `event19` and `event20` are not the actual PCM microphone/audio streams.
